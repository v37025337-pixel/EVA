# Рабочий цикл обучения YADO

Successor принимает цель и сам выбирает допустимые стратегии, исполняет их,
проверяет результат, записывает ошибку или успех и решает следующий шаг.
Состояние хранится в SQLite с проверкой причинной последовательности событий.

Добавлены два контракта целей:

* `native_source`: отдельные обучающие примеры, проверочные примеры и запросы
  без ответов. V2 выбирает композиции из существующих операций; V3 расширяет
  обработку строк; V4 выводит поддерживаемое правило над целыми числами.
  Материализация использует AST-механизм V2 и исходную структуру V1.
* `library_discovery`: только цель `html_xml_parser`. V6 находит названия в
  живом каталоге PyPI, V5 проверяет файл и метаданные зависимости. Отдельное
  событие проверки сверяет замороженный результат с PyPI Simple.

Принятый исходник остаётся в памяти самого цикла. Следующая задача с совместимым
контрактом может его повторно использовать. Совместимость типов не считается
доказательством правильности: исходник заново проверяется на примерах новой
задачи. Провал возвращает цикл к выбору другой доступной стратегии. Неудачный
кандидат сохраняется как опыт и не попадает в пул принятых программ.

Поиск в памяти рассматривает до 16 последних различных принятых программ
совместимого типа. Для выбора используются только обучающие пары новой задачи.
Выбирается первая программа, прошедшая эти пары; затем отдельный этап проверяет
контрольную выборку. При неоднозначных обучающих примерах контрольные ответы не
используются для выбора другой программы. Если ни одна не подходит, цикл
сохраняет прежнее поведение: пробует самую новую и при неудаче рассматривает
доступные расширения грамматики.

Одна единица бюджета стратегии повторного использования допускает до 16 таких
проб; это не одна операция исполнения и не измерение процессорного времени.
Журнал `memory_retrieval` версии 2 сохраняет порядок проб, их предсказания либо
ошибки и связь с ранее принятым исходником. Повторные копии одинакового исходника
не вытесняют остальные программы из этого ограниченного пула. Старые события
без этой записи проверяются по прежнему правилу выбора самой новой программы.

Регрессионная последовательность «сжатие → разворот → сжатие» проверяет, что
более ранняя программа доступна после обучения другой задаче того же типа и
перезапуска. При бюджете 1 новые примеры сжатия решаются из памяти; отключение
памяти даёт `WITHHOLD`. Это исправление поиска написано ассистентом. Генерацию
поддерживаемых программ по примерам по-прежнему выполняет ядро.

Запуск из корня репозитория после установки объявленных зависимостей:

```bash
python -m successor build --output /tmp/yado-birth
python -m successor.active_run --manifest /tmp/yado-birth/manifest.json --output /tmp/yado-run
python runtime/yado_full_regression_v1.py --manifest /tmp/yado-birth/manifest.json
```

`active_run` выполняет 20 целей, включая пять публичных наборов Exercism,
перезапуск, повторное применение исходника и живую проверку библиотеки.
Каталог результата должен быть новым. В нём сохраняются `receipt.json`, точные
записи событий, SQLite-состояние, задачи и сгенерированные исходники. Повторное
открытие этого состояния требует того же manifest, архива опыта и исходников.
GitHub Actions сохраняет их вместе как артефакт проверки.

Тесты также сравнивают поведение с отключённой памятью, отвергают неверные
проверочные ответы и проверяют восстановление между созданием исходника и его
независимой проверкой. Исходник возникает до доступа генератора к проверочным
ответам; генератор получает только обучающие пары.

Граница результата: набор задач и связующий код написаны ассистентом; выбор
стратегии и генерация поддерживаемой программы выполняются YADO внутри
ограниченной исходной грамматики. Публичные задачи уже использовались в прошлых
экспериментах: это проверка переноса в рабочий цикл, а не новый неизвестный
бенчмарк. Библиотеки читаются без установки и исполнения. Произвольное
самопереписывание, самостоятельный фоновый запуск, общий разум и сознание
этими проверками не установлены.

## Подцели из собственной истории неудач

`DevelopmentLoop` самостоятельно выбирает прошлую цель со статусом `WITHHOLD`,
если в разрешённом наборе остались непроверенные стратегии, а выделенный бюджет
позволяет их проверить. Приоритет определяется наблюдаемыми успехами стратегий
и их стоимостью. Вход API задаёт общий бюджет и предел числа подцелей; ID задачи,
новые примеры или список действий ему не передаются.

В журнале сохраняется связь `DEV_SELECT → COG_GOAL → COG_FINISH → DEV_OUTCOME`.
Проверка состояния заново выводит выбор из предшествующих событий и проверяет
бюджет, происхождение подцели и её результата. Для каждой подцели сразу
резервируется весь бюджет; неизрасходованный остаток резерва в этой сессии не
переиспользуется. В новых сессиях политика `verified_memory_context_v3` разрешает
повторную попытку после изменения доступного набора проверенных программ.
Тот же набор памяти повторно не проверяется; дубликаты программ, ошибки и
несовместимые входные типы не открывают повтор. Старые сессии сохраняют прежнюю
политику выбора. История абляций и остановленные задачи исключены. Чужая активная задача
приостанавливает развитие до её завершения. Автоматически планируются только
локальные `native_source` и `numeric` цели.

```bash
python -m successor development-start --manifest /tmp/yado-birth/manifest.json --state /tmp/yado-run/kernel.sqlite --budget 12 --max-goals 2
python -m successor develop --manifest /tmp/yado-birth/manifest.json --state /tmp/yado-run/kernel.sqlite --max-steps 100
python -m successor development-status --manifest /tmp/yado-birth/manifest.json --state /tmp/yado-run/kernel.sqlite
```

`development-stop --session-id ID` сохраняет остановку сессии и её текущей
подцели. Продолжение после перезапуска использует то же состояние. Каждый вызов
`develop` имеет предел шагов; создание подцели атомарно записывает два события.
Фоновый процесс не запускается. Если подходящих неудач нет, сессия завершается
без создания задач.

Воспроизводимый эксперимент с начальными неудачами, перезапуском и контролями:

```bash
python -m successor.development_run --manifest /tmp/yado-birth/manifest.json --output /tmp/yado-development-run
```

В нём ядро выбирает повторное решение двух задач, сохраняет программы и применяет
их на новых входах с бюджетом 1. Контроли используют те же новые входы и бюджет:
первый — состояние до развития, второй — состояние после развития с отключённой
памятью. Проверочные ответы не подаются генератору. При повторном решении
используется прежняя проверочная выборка; отдельный перенос проверяется на
других входах. Контракты и ожидаемые ответы написаны ассистентом.

Этот механизм доказывает выбор подцели из опыта и причинное использование памяти
в ограниченной задаче. Он не доказывает самостоятельное изобретение новых целей,
общий интеллект или сознание. Канонические G2/G3-состояния и условия допуска
эксперимента `yado_endogenous_deficit_discovery_v1` не изменяются.

## Единый возобновляемый цикл

`AutonomousLoop` связывает выбор следующей задачи и её выполнение. Он сначала
ищет проверенную неудачу, для которой осталась допустимая непроверенная стратегия
и хватает бюджета. Выбор использует тот же механизм оценки опыта, что и
`DevelopmentLoop`. Если такой задачи нет, ядро формирует новый экземпляр задачи
из собственной истории и текущих ошибок прогноза.

Исследование ограничено тремя заранее написанными грамматиками: отношения,
последовательности событий и кубические числовые зависимости. Для числовой задачи
начальный бюджет 3 может оказаться недостаточным. Тогда следующий цикл сам
выбирает повторную попытку с расширенным бюджетом; успешный опыт меняет стратегию
на последующих новых входах. Давление дефицита делится на число исследованных
в этой сессии задач соответствующего домена плюс один, чтобы один домен не
вытеснял остальные. Это заданная политика исследования, не самостоятельно
изобретённая мотивация. Внешние действия этим циклом не выполняются.

```bash
python -m successor autonomy-start --manifest /tmp/yado-birth/manifest.json --state /tmp/yado-run/kernel.sqlite --budget 120 --max-cycles 20
python -m successor autonomy-run --manifest /tmp/yado-birth/manifest.json --state /tmp/yado-run/kernel.sqlite --max-steps 1000
python -m successor autonomy-status --manifest /tmp/yado-birth/manifest.json --state /tmp/yado-run/kernel.sqlite
```

После первого запуска повторяется только `autonomy-run`: он продолжает ту же
сессию и незаконченную задачу. Лимит отдельного вызова — 1000 шагов, сессии —
64 цикла и 512 единиц зарезервированного бюджета. Один цикл — одна попытка цели;
повторное решение после неудачи занимает следующий цикл. Неиспользованный остаток
бюджета завершённой цели не возвращается в резерв сессии. `COMPLETE` означает
исчерпание заданного предела, а не успех всех задач.

`AUTO_SELECT` и связанная цель записываются одной транзакцией. После исполнения
проверка и отражение результата идут через прежний когнитивный цикл.
`AUTO_OUTCOME` связывается с терминальным событием и точным результатом. При
восстановлении заново вычисляются выбор, происхождение, бюджет и результаты.
Провал не стирается. Повторная неудача по тому же контракту не запускает
бесконечные повторы. Новая внешняя задача или активная сессия развития
приостанавливает автономный цикл до завершения чужой работы.

`autonomy-stop --session-id ID` останавливает сессию и принадлежащую ей задачу.
Перезапуск не отменяет остановку и не повторяет уже записанное исполнение.
Для изменения самого контроллера требуется новая проверенная идентичность;
старые SQLite-базы не перепривязываются заменой поля identity.

Этот цикл запускается обычным процессом, завершается по заданному пределу и
сохраняет состояние для следующего запуска. Службу постоянного хостинга он не
создаёт. Общее мышление вне поддерживаемых грамматик и появление сознания
этим механизмом не установлены.
